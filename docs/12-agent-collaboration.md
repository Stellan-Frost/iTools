# 12 · Agent 与 Subagent 协作

> 定位：定义根 Agent / 实施 Agent 的分工、并行派发的文件所有权规则、报告与验收格式；每次派发任务前照此执行。
> 状态：生效中。该流程已在阶段 3–9 反复使用（如阶段 6 四个 subagent 文件零重叠、阶段 8 三个 subagent）。
> 代码入口：无（纯流程文档）；派发对象是 `.workbuddy/` 外的仓库代码与文档。

## 1. 当前事实

- **根 Agent**：规划、冻结契约、划分文件所有权、并行派发、集成、跨包接线、冲突处理、跑全量门禁、更新文档与决策记录。
- **实施 Agent（subagent）**：在获派的文件白名单内实现与测试，报告实际输出；不得越界、不得改契约、不得自行 `pnpm install`（依赖由根 Agent 预装）。
- 已验证的节奏：根 Agent 先写 `contracts` + 包骨架 + 测试替身 → 并行派发互不重叠的实施 Agent → 根 Agent 集成并修接口缝隙 → `pnpm verify` 全绿后单次提交。

## 2. 派发前根 Agent 必须完成

| 步骤 | 产物 |
| --- | --- |
| 1. 冻结共享契约 | `packages/contracts/src/*.ts`、`*/src/application/ports.ts`、领域类型文件 |
| 2. 冻结测试替身 | `src/test-support/**`（被 `tsconfig.build.json` 排除，不进 dist） |
| 3. 预装依赖 | 改 `package.json` + `pnpm install`；实施 Agent 不得再装 |
| 4. 划分文件所有权 | 每个 Agent 一份「允许创建/修改」与「禁止修改」清单，逐文件列出 |
| 5. 定义完成判据 | 必须运行的精确命令 + 期望输出（测试数、通过状态） |

## 3. 派发模板（每份任务书必备）

1. 目标与**不做事项**（明确范围外，防止范围膨胀）。
2. 允许修改的文件/目录（逐项）；禁止修改的文件（含冻结契约、他人文件、`docs/**`、`package.json`）。
3. 已冻结接口与可直接导入的依赖（带路径与签名）。
4. 具体实现要求：数据形状、签名、语义规则、命名、i18n 键、性能约束（N+1、超时）。
5. 工程约束：TS strict + `exactOptionalPropertyTypes` + `noUncheckedIndexedAccess` + `verbatimModuleSyntax`、NodeNext 相对导入带 `.js`、禁止 `any`/`@ts-ignore`/`eslint-disable`/`console.*`、单文件 ≤400 行。
6. 必须运行的命令（精确到文件）与「只要求自己的测试全绿，不跑整仓 verify」。
7. 交付报告要求（见 §5）。
8. 等待策略：依赖他人交付的文件不存在时，等待重试（如 30 秒 × 5 次），**禁止自己代写他人文件**。

## 4. 并行纪律（零重叠）

- 不同 Agent **不得**并行修改：同一契约文件、同一聚合入口（如 `i18n/resources/index.ts`）、同一测试文件、`package.json`、`tsconfig*`。
- 集成测试若都要重置数据库 schema，必须各自用独立 schema（阶段 8 的教训：两个测试并行 `drop schema public` 互相踩）。
- 根 Agent 集成时优先修「接口缝隙」：重复导入、推断类型偏差（如 TypeBox `locale` 被推断为 `never`）、组装参数错位、生产/开发分支行为不一致。
- 分支：任务在 `main` 上以单次提交落地；提交信息用 `feat:/fix:/docs:` + 中文摘要 + 要点列表。

## 5. 报告与验收

实施 Agent 必须报告：

1. 改动文件清单（新增/修改/删除）。
2. 实际执行的命令与**输出尾部**（测试数量、通过状态）；未执行的命令不得声称通过。
3. 等待重试情况（若依赖并行交付）。
4. 实现要点、未覆盖项、风险、需要根 Agent 裁决的问题。

根 Agent 验收动作：核对变更范围与所有权 → 跑集成测试 → `pnpm verify` → 更新 `docs/13` 决策与模块文档 → 单次提交并记录 hash。最终回复必须包含：提交 hash、逐项验收对照、已知限制、下一步门槛。

## 6. 禁止事项

| ❌ 错误做法 | ✅ 正确做法 |
| --- | --- |
| 实施 Agent 改冻结契约或他人文件 | 报告冲突，由根 Agent 裁决 |
| 根 Agent 把未确认的架构决定写成「用户已批准」 | 标为「根 Agent 建议，待用户确认」或先问 |
| 派发时只给一句「实现 XX 功能」 | 按本文 §3 模板写全 8 项 |
| 用「应该没问题」替代命令输出 | 附实际输出尾部；失败如实报告 |
| 集成阶段顺手重设计他人实现 | 只修接口缝隙；如需重设计先提变更提案 |

## 7. 自主权限边界

- **可自主**：规划、并行开发、测试、修复、文档更新、本地集成验证。
- **须用户批准**：生产部署、生产数据库迁移、破坏性数据操作（含清空本地/生产数据）、公网安全配置变更、扩大产品范围（新增真实工具、改工具清单）。
- 未经批准的领域变更：只做方案对比，等用户拍板（参照 `.workbuddy` 既往模式：对比文档 → AskUserQuestion → 记入 Dxx）。

## 8. 已知限制

- subagent 模型与配额由平台决定，可能 429；此时根 Agent 顺延自行完成（本次文档重构即如此），不阻塞交付。
- 「根 Agent 当前模型」等描述不写入文档（会漂移），以任务书为准。
