# 14 · 分阶段实施计划（每阶段均有目标与验收标准）

> 原则：按依赖顺序推进；阶段未通过验收不得进入依赖它的下一阶段。验收只依据代码、自动化测试、构建产物和可复现证据，不接受“已完成”口头声明。所有验收均在隔离开发/测试环境进行；生产部署另行审批。

## 阶段 0：现状审计与基线冻结

**目标**
- 审查现有仓库、已有 Markdown 文档、代码与部署文件。
- 合并已有规范，不建立相互冲突的第二套架构。
- 输出真实目录树、实际技术栈、缺口与决策冲突表。
- 冻结已确认要求；未决事项单独登记，不擅自推断。

**实施任务**
- 检查 `package.json`、pnpm 锁文件、Workspace、Turborepo 配置、现有应用和测试。
- 将本目录文档与仓库原有文档逐项比对；标记保留、合并、废弃项。
- 确认工具注册表、数据库 Seed、路由、API Schema 与测试的现状。

**验收标准**
- [ ] 提交仓库目录树和包依赖图。
- [ ] 每项已确认决策均有对应文档位置；冲突均列入未决清单。
- [ ] 文档不将未实现功能描述为已实现。
- [ ] 根 Agent 审核现状与差异报告后，才可开始阶段 1。

## 阶段 1：Monorepo、代码规范与共享契约

**目标**
- 建立可重复安装、构建、测试的工作区。
- 先定义稳定契约和模块边界，防止各子 Agent 自行创造接口。

**实施任务**
- pnpm Workspace + Turborepo；TypeScript `strict`。
- 配置 ESLint、Prettier、包边界检查、环境变量 Schema。
- 建立共享 `contracts` 包与基础 API/错误/任务/工具契约。
- 为每个包声明唯一职责、公开入口和依赖方向。

**验收标准**
- [ ] 全新克隆后按文档命令可安装依赖。
- [ ] `lint`、`typecheck`、`test`、`build` 命令存在且可运行。
- [ ] TypeScript strict 检查通过；包依赖边界检查通过。
- [ ] 共享契约有类型测试/契约测试；不允许工具包互相依赖。
- [ ] 锁文件提交并可复现安装；不得用未锁定依赖替代锁文件。

## 阶段 2：设计系统与全局应用壳

**目标**
- 建立唯一的 MD3 设计系统和可复用应用骨架。
- 确保首页、分类页、工具页和管理后台使用统一主题与布局规则。

**实施任务**
- 完成鸭青主题语义 Token、浅色/深色主题、MD3 五类十五角色字体、图标和动效 Token。
- 实现主题适配层、导航、搜索命令面板、通用卡片、表单、对话框、任务状态与错误反馈。
- 采用响应式布局和共享页面骨架，不复制基础 UI 组件。
- 不开展独立无障碍专项；不得因此破坏控件的基本交互功能。

**验收标准**
- [ ] Token 与组件适配层有使用说明和示例。
- [ ] 首页、分类页、工具页、后台在桌面与移动视口可正常布局。
- [ ] 组件样式来自统一 Token；无未经说明的散落品牌色/间距/圆角常量。
- [ ] 关键控件交互和错误反馈通过组件测试。
- [ ] 视觉检查记录覆盖主题、导航、表单、对话框、任务与结果状态。

## 阶段 3：应用路由、SSR、国际化与 SEO

**目标**
- 建立可索引、双语、服务端正确返回状态码的页面框架。

**实施任务**
- React + Vite；Fastify 提供 SSR 和静态资源托管。
- 实现 `/zh-CN/...` 与 `/en/...` 路由、i18next 命名空间。
- 实现工具目录查询、真实 404、Sitemap、robots、canonical 和语言关联链接。

**验收标准**
- [x] 中英文首页、分类页和工具页可直达访问。
- [x] 不存在或停用的工具 URL 返回 HTTP 404，而非 HTTP 200 伪 404。
- [x] 全局搜索、分类页、首页和 Sitemap 仅展示实现存在且启用的工具。
- [x] SSR 的语言、title、description、canonical 和语言关联链接正确。
- [x] 路由、目录状态和 SEO 相关集成测试通过。

> 验收顺序（D06，2026-10-19 用户确认）：阶段 3 只验收不依赖数据库与任务运行时的部分；目录来源为代码注册表。数据库启用状态、Seed 一致性与结果持久化相关的完整集成验收移至阶段 7 之后。阶段 3 的冻结接口、文件所有权与验收矩阵见 [20 · 阶段 3 冻结](20-stage-3-routing-ssr-i18n-seo.md)。

## 阶段 4：工具注册表与统一工具页面

**目标**
- 建立新增工具的唯一注册流程，避免后台启用不存在的工具。
- 让每个工具通过稳定契约接入统一页面、任务和文件系统。

**实施任务**
- 实现代码注册表、能力声明、Schema、Worker adapter、错误映射与文案键。
- 实现工具页统一骨架、输入验证、参数区、结果区和开源致谢区。
- 实现注册表、Seed、数据库的一致性检查。

**验收标准**
- [ ] 至少一个测试工具可完整通过注册、路由、输入校验、执行和结果展示流程。
- [ ] 重复 ID、非法路由、不兼容能力声明会阻断 CI。
- [ ] 数据库不得启用注册表中不存在的工具。
- [ ] 新工具契约测试可独立运行；工具之间没有直接耦合。
- [ ] 工具页统一区块顺序和错误状态通过 E2E 测试。

## 阶段 5：任务运行时与 Worker

**目标**
- 让所有工具共用一致的任务状态、队列、进度、取消、错误和资源预算。

**实施任务**
- 实现任务状态机、FIFO 调度器、资源感知并发限制、Worker 池和工具适配器。
- 定义取消确认、Worker 强制终止/重建、结果提交与失败释放资源规则。
- 页面切换不应意外销毁全局任务。

**验收标准**
- [ ] 所有合法状态转换有单元测试；非法转换被拒绝。
- [ ] 排队、执行、成功、失败、取消、超限和重试路径有测试。
- [ ] 取消/失败后释放 Worker 与临时资源。
- [ ] 并发任务不突破集中配置的资源上限。
- [ ] 结果未成功持久化时任务不得标记 completed。
- [ ] 页面路由切换测试证明任务生命周期由全局运行时管理。

## 阶段 6：本地文件资产与 IndexedDB

**目标**
- 统一管理源文件、中间文件、结果和任务引用，确保浏览器本地数据不被意外清理或外传。

**实施任务**
- 实现 IndexedDB repository、资产引用关系、Object URL 生命周期、存储配额提示、清理与归档导入导出。
- 按源文件默认保留 7 天；清理时跳过正在使用或仍被引用的源文件。
- 在实施任何结构性清库前解决第 108 题与长期保留要求之间的冲突。

**验收标准**
- [ ] 文件资产增删改查、引用关系和 Object URL 释放有测试。
- [ ] 配额不足、部分写入失败、导入失败不会破坏已有结果。
- [ ] 清理任务不会删除活动任务依赖的源文件或已完成结果。
- [ ] 归档导入校验版本、引用、容量；失败时现有数据保持不变。
- [ ] 浏览器网络审计证明文件和处理结果未上传。
- [ ] 未获明确批准前，生产数据不得因版本升级而自动清空。

## 阶段 7：后端、数据库与 API

**目标**
- 建立可验证的服务端数据层、类型安全 API 和可追踪的数据库迁移。

**实施任务**
- Fastify + PostgreSQL + Drizzle ORM/Kit + TypeBox。
- 建立工具目录、双语元数据、元数据版本与管理员会话表。
- 从实际 Fastify 路由/Schema 生成 OpenAPI。
- 配置应用内连接池、超时、空闲回收、优雅关闭和健康检查。

**验收标准**
- [ ] 新环境可通过版本化迁移和 Seed 初始化。
- [ ] 关键约束由数据库唯一键、外键和事务保障。
- [ ] API 输入输出均经 Schema 校验，错误结构和 HTTP 状态码一致。
- [ ] OpenAPI 与真实路由/Schema 一致，CI 差异检查通过。
- [ ] 同一主版本兼容性测试通过。
- [ ] 无效关键配置导致启动失败且日志不泄露秘密值。

## 阶段 8：唯一管理员与管理后台

**目标**
- 允许唯一管理员安全管理工具可用性与展示元数据，不引入普通用户登录或多管理员协作。

**实施任务**
- 实现一次性初始化、会话 Cookie、CSRF、来源检查、服务端授权、固定速率限制。
- 实现工具启停、分类排序、双语元数据编辑、版本预览与回滚。
- 密码恢复只通过服务器管理权限下的专用命令。

**验收标准**
- [ ] 不存在公开注册或普通用户账户系统。
- [ ] 初始化令牌一次性使用；初始化完成后入口关闭。
- [ ] 未认证/无权/CSRF 失败请求均被服务端拒绝。
- [ ] 会话过期、轮换、主动撤销与恢复命令有测试。
- [ ] 元数据版本回滚通过版本检查且不会静默覆盖较新修改。
- [ ] 登录固定速率限制生效；没有渐进延迟或永久锁定逻辑。

## 阶段 9：安全、隐私与依赖治理

**目标**
- 把隐私边界、CSP、限流、日志和依赖扫描变成可自动验证的规则。

**实施任务**
- 默认拒绝的 CSP；外部来源必须审核用途、数据流与影响，优先本地托管。
- 公开只读 API 与管理写 API 使用不同保护等级。
- 锁定依赖并扫描漏洞；严重且可利用漏洞阻止合并。
- 日志最小化并保留 30 天。

**验收标准**
- [ ] CSP 与关键安全响应头自动化检查通过。
- [ ] 未审核外部资源不能被加入生产 CSP。
- [ ] 管理写请求的认证、服务端授权、CSRF 与来源检查有负向测试。
- [ ] 日志中不存在凭据、文件内容、结果内容或敏感参数。
- [ ] 依赖漏洞扫描接入 CI；严重且可利用漏洞阻断合并。
- [ ] 一般安全检查警告与硬性门禁在 CI 中清晰区分。

## 阶段 10：PWA、缓存与更新

**目标**
- 支持已缓存应用离线打开，并按已确认的“更新时清空应用缓存并重新下载”策略更新。

**实施任务**
- 预缓存应用代码和基础资源；重型引擎按需缓存。
- 更新提示由用户确认；存在运行任务时显示中断风险。
- 应用缓存与 IndexedDB 数据分离，更新不得清空 IndexedDB。

**验收标准**
- [ ] 首次安装、离线启动、未缓存引擎、更新拒绝与下载失败均有测试。
- [ ] 更新不会静默中断运行任务。
- [ ] 清理 Cache Storage 不会删除 IndexedDB 数据。
- [ ] 下载失败时显示明确恢复步骤；不得声称旧缓存仍可用，除非测试证实。
- [ ] 动态 API、认证响应和敏感数据不进入共享缓存。

## 阶段 11：CI、性能与质量门禁

**目标**
- 每次合并前自动检查类型、测试、契约、构建、依赖边界、隐私和性能。

**实施任务**
- GitHub Actions 执行 lint、typecheck、Vitest、Playwright、build、OpenAPI diff、注册表/Seed 一致性、漏洞扫描。
- 对首页、分类页、工具页和重型引擎分别建立性能预算；先测量基线，再确认阈值。

**验收标准**
- [ ] PR 检查可在干净环境复现。
- [ ] 任一硬性检查失败都会阻止合并。
- [ ] 一般安全警告不会被错误配置成与严重漏洞相同的门禁。
- [ ] 性能预算有真实基线、阈值、测量方法和报告。
- [ ] 重型引擎按需加载并独立计入预算。
- [ ] E2E 覆盖首页、搜索、工具直达、任务处理、后台登录和错误路径。

## 阶段 12：部署、备份与恢复准备

**目标**
- 交付可审核、可复现的部署配置和故障恢复流程，但不自动发布生产。

**实施任务**
- Docker Compose、反向代理模板、网络规则、健康检查与部署脚本纳入 Git。
- 密钥通过环境变量或只读秘密文件注入。
- 应用健康检查持续失败达到阈值时，自动回滚上一稳定镜像与配置。
- 数据库迁移失败立即停止发布并保留现场；恢复/重试方案由授权人员审批。

**验收标准**
- [ ] 配置、脚本和镜像版本可追溯；秘密不在 Git 和镜像中。
- [ ] 源站不能绕过代理被公网直接访问。
- [ ] 应用回滚演练可复现，且不触发数据库自动反向迁移。
- [ ] 迁移失败会停止发布并输出诊断信息，不执行破坏性自动回滚。
- [ ] 备份任务、保留策略、加密和失败告警均有可验证记录。
- [ ] 文档明确 RTO 24 小时、RPO 24 小时及“尚未定期恢复演练”的限制。

## 阶段 13：全局验收与交付

**目标**
- 汇总可复现证据、已知限制和生产变更计划，交由用户审核。

**实施任务**
- 执行 `13-acceptance-open-decisions.md` 全量清单。
- 整理测试报告、变更清单、依赖清单、数据库迁移计划、备份/恢复说明、回滚计划。
- 核对所有子 Agent 的完成报告和文件变更范围。

**验收标准**
- [ ] 所有硬性测试通过，或未通过项被明确列为阻塞，不得标记完成。
- [ ] 每个阶段有目标、验收记录、证据链接和负责人。
- [ ] 已知限制、未决决策、风险与未覆盖测试完整列出。
- [ ] 根 Agent 审核文档与代码一致。
- [ ] 形成部署计划并等待用户明确批准；不得自动部署生产。

## 所有阶段通用的代码质量验收

每个阶段都必须额外满足 `15-mandatory-code-requirements.md` 中的五项强制要求：可读性、模块化与低耦合、统一命名、单一实现来源、清晰分层。阶段验收不得只检查功能是否运行，还必须检查代码结构和复用情况。

- [ ] 文件职责单一；无集中多种业务职责的超大文件。
- [ ] 模块依赖方向清晰，并由自动化规则约束。
- [ ] 命名统一且能表达用途。
- [ ] 复用已有实现；重复实现必须说明不可复用的业务原因。
- [ ] 新增代码位于明确的架构层级，公共能力放入唯一的共享模块。

## 阶段推进规则
- 不跳过前置阶段；如果并行开发，必须先冻结所依赖的接口。
- 每阶段的“完成”意味着验收证据存在，不等同于文档已写好。
- 测试失败、契约冲突、隐私边界不清或破坏性行为未获批准时，阶段状态为 `blocked`。
- 任何与既定用户决策不一致的实现，必须先提交变更提案，不得静默改动。
